# FocusFlow Linux Desktop Design

**Date:** 2026-04-27

## Goal

将当前纯前端 `FocusFlow` 待办番茄钟迁移为 Linux 平台下可离线运行的桌面应用，保留现有页面视觉与主布局，仅补充最少量桌面集成能力。首版必须支持：

- 桌面通知与到点提醒
- 系统托盘
- 开机自启

## Current Project Context

当前项目是一个纯静态单页应用：

- `index.html`：主界面结构
- `styles.css`：视觉样式
- `app.js`：待办、番茄钟、统计、`localStorage` 持久化逻辑

现有功能包括：

- 待办新增、完成、删除、筛选
- 专注 / 短休息 / 长休息三种模式
- 番茄钟开始、暂停、重置、跳过
- 自定义时长
- 今日统计
- 浏览器通知、声音提醒、`localStorage` 持久化

当前项目没有构建工具链，也不是 Git 仓库。

## Constraints

- 保留现有前端设计与主界面布局，不做整体视觉重构
- 首版优先保证 Linux 可用，不扩展 Windows / macOS 特化能力
- 应用必须支持纯本地离线运行
- 系统能力属于增强层，不应阻断待办与计时核心流程
- 主业务状态继续由前端维护，避免首版将计时与任务逻辑重写进 Rust

## Chosen Approach

采用 `Tauri + 现有 HTML/CSS/JS 前端` 的桌面化方案。

### Why This Approach

1. 现有前端可以最大程度复用，迁移成本最低
2. `Tauri` 在 Linux 下可提供托盘、通知、自启、窗口管理等桌面能力
3. 相比 `Electron`，包体与资源占用更适合当前工具型应用
4. 相比原生 GTK / Qt 重写，能更好满足“保留原有前端设计”的约束

### Alternatives Considered

#### Electron

优点：

- 桌面能力成熟
- 生态资料丰富

缺点：

- 包体与运行时资源占用明显更高
- 对当前简单单窗口工具来说过重

#### GTK / Qt 原生重写

优点：

- 原生感更强

缺点：

- 几乎无法复用现有前端
- 重写成本高，不符合当前目标

## Architecture

应用分为两层：

### 1. Frontend Layer

继续承载主要业务逻辑与界面渲染：

- 待办事项状态
- 番茄钟模式与倒计时
- 今日统计
- 界面交互与样式表现

### 2. Desktop Integration Layer

由 `Tauri` 提供系统级能力：

- Linux 窗口生命周期管理
- 系统托盘
- 桌面通知
- 自启注册与查询
- 可能的提醒音桥接

前端层不直接处理 Linux 平台细节；桌面层不接管待办与计时业务。

## Component Boundaries

### Web UI

职责：

- 保留现有顶栏、任务面板、计时面板、统计面板布局
- 保留现有主色、排版与控件风格
- 在不破坏主界面的前提下增加最少桌面入口

首版允许的新增 UI：

- 小型“设置”入口，放置在现有主界面中不打断布局的位置
- 设置项仅包含：
  - 桌面通知开关 / 测试通知
  - 开机自启开关
  - 托盘行为说明或开关（如默认关闭到托盘）

不做事项：

- 不重做导航结构
- 不新增独立设置页
- 不大幅改动视觉层次

### Timer and Todo State

职责：

- 保留现有 `app.js` 里的核心状态模型
- 继续由前端驱动任务、计时、统计
- 将持久化访问收敛到可替换的存储适配层

设计要求：

- 对现有 `localStorage` 使用点做一层简单封装
- 首版可继续使用 WebView 可访问的本地持久化
- 未来如需迁移到 `Tauri` store 或本地文件，不改变业务接口

### Desktop Bridge

职责：

- 暴露桌面通知能力给前端
- 暴露托盘状态更新与托盘菜单事件
- 暴露自启读取与切换
- 暴露窗口显示 / 隐藏 / 聚焦操作

边界要求：

- 前端只调用清晰的桌面 API，不感知底层 Rust 细节
- Rust 层不持有待办列表与番茄业务状态

### System Tray

职责：

- 应用启动后创建托盘
- 支持从托盘恢复主窗口
- 支持从托盘开始 / 暂停计时
- 支持退出应用

托盘最低菜单：

- 显示窗口
- 开始或暂停计时
- 退出

### Auto Start

职责：

- 读取当前是否已启用开机自启
- 切换启用 / 关闭状态
- 失败时返回明确错误

## Data Flow

### App Startup

1. `Tauri` 启动桌面壳与主窗口
2. 前端加载本地状态
3. 前端渲染主界面
4. 桌面层初始化托盘与自启状态
5. 前端把当前计时模式、运行状态、剩余时间同步给托盘展示层

### User Interaction

1. 用户在界面操作待办、模式或计时器
2. 前端更新本地状态
3. 前端写入本地持久化
4. 若状态影响桌面能力，则调用桌面桥接：
   - 更新托盘菜单状态
   - 更新通知文案上下文

### Timer Completion

1. 前端检测当前专注或休息倒计时结束
2. 前端完成当前模式结算与下个模式切换
3. 前端调用桌面桥接发送：
   - 桌面通知
   - 提醒音
   - 托盘状态刷新
4. 前端继续渲染新模式状态

### Tray Interaction

1. 用户点击托盘菜单
2. `Tauri` 接收系统菜单事件
3. 桌面层将事件转发给前端
4. 前端执行对应动作并刷新界面与持久化

## Window and Background Behavior

首版窗口策略：

- 主窗口为单窗口应用
- 关闭按钮默认不直接退出，而是隐藏到托盘
- 托盘“退出”执行完整退出
- 从托盘恢复时显示并聚焦主窗口

计时器后台策略：

- 计时逻辑仍在前端
- 不依赖页面持续高频渲染来判断真实经过时间
- 必须基于时间戳校正剩余秒数，避免窗口隐藏或系统调度导致明显漂移

## Notification Behavior

通知触发场景：

- 专注结束，进入短休息或长休息
- 休息结束，进入专注

通知内容要求：

- 明确当前结束的是哪种模式
- 明确即将进入的下一种模式
- 若当前有选中的专注任务，通知中优先带出任务名称

降级策略：

- Linux 桌面通知不可用时，不中断计时逻辑
- 回退为应用内 toast
- 若提醒音无法播放，通知仍然发送

## Persistence

首版保持以下持久化内容：

- 待办列表
- 当前选中任务
- 当前筛选条件
- 番茄钟模式与剩余时长
- 自定义时长配置
- 番茄完成统计
- 自启偏好与通知偏好

持久化要求：

- 启动后能够恢复上次的业务状态
- 因异常数据导致读取失败时，回退默认状态，不使应用启动失败

## Error Handling

### Notification Failures

- 通知服务不可用：记录错误，回退 toast
- 通知权限异常：不阻断主流程

### Tray Failures

- 托盘初始化失败：主窗口与核心业务仍正常运行
- 托盘菜单部分事件失败：提示用户，但不破坏当前状态

### Auto Start Failures

- 自启开启失败：在界面中提示失败原因
- 自启状态读取失败：界面显示未知状态，并允许重试

### Persistence Failures

- 解析失败或字段不合法：回退默认状态并继续启动

## Packaging and Runtime Expectations

首版目标平台为 Linux 桌面环境。

交付要求：

- 可在常见 Linux 桌面环境中启动
- 有标准桌面应用窗口
- 有托盘图标
- 支持本地安装与本地运行

首版不要求：

- 跨发行版深度兼容承诺
- 多窗口
- 云同步
- 账户系统
- 原生数据库

## Testing Strategy

### Functional Verification

- 待办新增、完成、删除、筛选正常
- 专注 / 短休息 / 长休息切换正常
- 开始、暂停、重置、跳过正常
- 今日统计计算正常
- 重启应用后状态可恢复

### Desktop Verification

- 桌面通知可触发
- 专注与休息结束时有到点提醒
- 托盘菜单可显示窗口、开始或暂停、退出
- 关闭主窗口后应用仍驻留托盘
- 从托盘可恢复窗口
- 自启可以切换并在下次登录生效

### Regression Verification

- 原有界面主布局与视觉风格保持一致
- 原有计时与统计逻辑无明显行为回退

## Acceptance Criteria

当以下条件全部满足时，首版 Linux 迁移视为完成：

1. 应用可以作为 Linux 桌面应用启动
2. 当前 Web 版主界面视觉与布局基本保持一致
3. 待办、番茄钟、统计、本地持久化继续可用
4. 专注结束与休息结束都能触发桌面通知与提醒
5. 应用可驻留系统托盘，并从托盘恢复窗口
6. 托盘菜单至少支持“显示窗口 / 开始或暂停 / 退出”
7. 应用支持开机自启开关
8. 任一桌面增强能力失败时，核心待办与计时流程仍能使用
